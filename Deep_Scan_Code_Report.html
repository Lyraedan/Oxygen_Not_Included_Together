Kritisch [ClientRpc] ohne IncludeHost in allen Tool-Syncern verhindert Host-Ausführung
ONI_Together/Networking/OxySync/Components/Tools/*ToolSyncer.cs

In feature/oxysync-all-tools verwenden alle Tool-Klassen (Dig, Build, Deconstruct, Attack, Capture, Sandbox etc.) das Muster [Command] -> CallClientRpc(nameof(RpcXxx)). In NetworkBehaviour.cs schließt CallClientRpc den Host standardmäßig aus, solange IncludeHost = true nicht gesetzt ist.

Fehlerhafter Code-Ablauf
// Client ruft Graben auf -> Command an Host
[Command]
private void CmdDig(int cell, int animationDelay, int priority_class, int priority_value)
{
    // Sendet via PacketSender.SendToAllClients an Clients.
    // Host führt RpcDig NICHT aus, weil IncludeHost = false (Default)!
    CallClientRpc(nameof(RpcDig), cell, animationDelay, priority_class, priority_value);
}

[ClientRpc] // FEHLT: (IncludeHost = true)
private void RpcDig(int cell, int animationDelay, int priority_class, int priority_value)
{
    DigTool.PlaceDig(cell, animationDelay); // Läuft nur auf Clients, NIE auf dem Host!
}
Lösung
Entweder [ClientRpc(IncludeHost = true)] deklarieren ODER im CmdXxx die Aktion direkt auf dem Host ausführen (wie in MoveToLocation.cs). Außerdem muss in RpcXxx der auslösende Client die Aktion ignorieren, da er sie lokal schon ausgeführt hat.
Kritisch Storage-Sync löscht Atmo-Anzüge und tötet lebende Tiere in Fallen
ONI_Together/Misc/BuildingUtils.cs:140-145

In BuildingUtils.ClearStorage wird vor dem Wiederaufbau aus dem Byte-Blob jedes Element im Container mit DeleteObject() zerstört. Danach wird das Prefab anhand des Tags neu instanziiert.

Fehlerhafter Code
private static void ClearStorage(Storage storage)
{
    for (int i = storage.items.Count - 1; i >= 0; i--)
        storage.items[i].DeleteObject(); // Zerstört echte Anzüge & Tiere!
    storage.items.Clear();
}
Lösung (Siehe PR #175)
Entitäten mit Assignable (Anzüge) und GameTags.Creature (Tiere) dürfen weder in den Blob codiert noch in ClearStorage gelöscht werden.
Kritisch Steamworks 2-Spieler Ready-Screen Deadlock
ONI_Together/Networking/ReadyManager.cs:193-197

In ReadyManager.RefreshReadyState() prüft die Methode ConnectedPlayers.Count <= 1, um den Broadcast zu überspringen, wenn nur noch der Host im Spiel ist. Bei Steamworks ist der Host jedoch nicht in seiner eigenen ConnectedPlayers-Liste (Roster = 1 bei 2 Spielern).

Fehlerhafter Code
if (MultiplayerSession.ConnectedPlayers.Count <= 1)
{
    AllClientsReadyPacket.ProcessAllReady(); // Feuert nur lokal beim Host!
    return; // Client erhält NIE das AllReady-Signal und bleibt ewig im Screen stecken!
}
Lösung (Siehe PR #125)
Die Prüfung muss Spieler zählen, die ungleich der eigenen ID sind (others > 0), statt der rohen Roster-Größe.
Hohes Risiko LAN Reconnect ändert Client-ID (Session-Desync nach Weltexport)
ONI_Together/Networking/Transport/Lan/LiteNetLibServer.cs:153

In OnConnectionRequest wird die ID aus peer.Id + 2 generiert. LiteNetLib vergibt nach dem Socket-Schließen beim Welt-Laden eine inkrementierte peer.Id (z.B. von 0 auf 1). Der wiederkehrende Spieler wird zu ID 3 statt 2. Cursors und Besitzrechte gehen verloren.

Lösung
Den persistenten CLIENT_ID-Handshake aus Commit 7fda4151 wiederherstellen oder Reconnect-Mapping via IP/Token führen.
Hohes Risiko Off-Screen Rohre und Leitungen synchronisieren niemals (Trockenlaufen)
ONI_Together/Networking/Components/ConduitFlowSyncer.cs:180-182

Rohrzellen werden verworfen, wenn kein Spieler die Zelle im Viewport hat (if (_recipientScratch.Count == 0) continue;). Selbst beim periodischen forceRefresh wird dieser Check nicht aufgehoben. Rohre außerhalb der Kamera divergieren dauerhaft zwischen Host und Client.

Lösung (Siehe PR #171)
Beim periodischen forceRefresh-Tick den Viewport-Check aufheben, damit mindestens alle paar Sekunden der gesamte Leitungszustand abgeglichen wird.
Hohes Risiko Memory Leak in MultiplayerSession.Clear() (Zerstörte GameObject-Referenzen)
ONI_Together/Networking/MultiplayerSession.cs:92-105

MultiplayerSession.Clear() leert das Wörterbuch PlayerCursors nicht und zerstört die Remote-Cursor-GameObjects nicht. Wird nach einer Session ein neues Spiel geladen, verweisen alte Cursors auf zerstörte Unity-Objekte, was zu NREs im Render-Loop führt.

Lösung
foreach (var c in PlayerCursors.Values) if (c != null) Object.Destroy(c.gameObject); PlayerCursors.Clear(); InActiveSession = false; in Clear() einfügen.
Mittleres Risiko Unbegrenzte Puffergröße in RpcSerializer führt zu OutOfMemory-Crash
Shared/OxySync/RpcSerializer.cs:418 & 270

In DecompressString liest BitConverter.ToInt32(gZipBuffer, 0) die ungepackte Länge und allokiert sofort new byte[dataLength] ohne Obergrenzen-Check. Bei fehlerhaften oder manipulierten Paketen stürzt der Spielprozess sofort mit OutOfMemoryException ab.

Lösung
Schutz einbauen: if (dataLength < 0 || dataLength > 10 * 1024 * 1024) return string.Empty;.
Mittleres Risiko GZip-Overhead & String-Null-Konvertierung in RpcSerializer
Shared/OxySync/RpcSerializer.cs:386-406

Kurze Strings wie "Tile" oder "DEFAULT_FACADE" werden mit GZip komprimiert und Base64-codiert. Das bläht kurze Texte auf das Neunfache auf und allokiert pro Parameter 5 Müllobjekte im GC. Zudem wird null zu string.Empty, was Facade-Lookups brechen kann.

Lösung
GZip nur bei Strings > 256 Bytes aktivieren; darunter normale UTF-8 BinaryWriter-Bytes schreiben.
Mittleres Risiko Mögliche NullReferenceException in StandardWorker_Patches.cs
ONI_Together/Patches/DuplicantActions/StandardWorker_Patches.cs:52

In StandardWorker_StartWork_Patch.Postfix auf dem Branch backup/worker-progress-bar-pause-2026-08-28 wird start_work_info.workable.GetType() aufgerufen. Ist start_work_info.workable == null, crasht der Patch mit einer NRE.

Lösung
Vor der Schleife einbauen: if (start_work_info.workable == null) return;.
Mittleres Risiko Ghost-NetIdentities durch GetNetIdentity()-Lookup
ONI_Together/Networking/Extensions.cs:42-44

GameObject.GetNetIdentity() hängt automatisch eine NetworkIdentity an, wenn keine existiert. Lookups gegen UI-Elemente oder temporäre Partikel erzeugen tausende Geister-Identities in der Registry (beschrieben in PR #176).

Lösung
Eine strikte Trennung einführen: TryGetNetIdentity hängt keine Komponente an, nur explizite Registrierungen dürfen AddComponent rufen.
