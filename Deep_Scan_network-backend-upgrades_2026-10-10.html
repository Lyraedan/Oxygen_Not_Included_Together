K1[TargetRpc] wird nie ausgeführt — der Ziel-RPC-Kanal ist tot
OxySync/Packets/ClientRpcPacket.cs:45-58

SendTargetRpcToPlayer packt einen [TargetRpc] in eine ClientRpcPacket mit gesetztem TargetPlayerId. Beim Empfang geht die Nachricht immer über InvokeClientRpc, das nur _clientRpcMethods durchsucht. [TargetRpc]-Methoden liegen in _targetRpcMethods (NetworkBehaviour.cs:213) — der Hash wird nie gefunden, der Aufruf still verworfen. InvokeTargetRpc existiert in beiden Adaptern, hat aber null Aufrufstellen im ganzen Repo. Das ist eine Regression: der frühere OxySyncDispatchResolver verzweigte anhand von TargetPlayerId == ulong.MaxValue.

Fehlerhafter Ablauf
public void OnDispatched()
{
    if (MultiplayerSession.IsHost) return;
    if (TargetPlayerId != ulong.MaxValue && TargetPlayerId != MultiplayerSession.LocalUserID)
        return;                                    // Ziel-Filter ok
    if (!SyncBehaviourResolver.TryResolve(NetId, BehaviourId, out var behaviour))
        return;
    behaviour.InvokeClientRpc(MethodHash, Args);     // TargetRpc lebt in _targetRpcMethods
}
Fix

In OnDispatched verzweigen: TargetPlayerId != ulong.MaxValue → InvokeTargetRpc, sonst InvokeClientRpc. Betroffen ist konkret die Positions-Recovery (OnServerPositionRequest → TargetRpcReceiveFullState, der Margin wurde in ebaa5ba5 auf 2 Chunks vergrößert) sowie NetworkTransform.TargetReceivePosition und OxySyncChat.TargetRpcReceiveHistory.

K2Bulk-Batches gehen leer raus, sobald die Paket-Queue aktiviert ist
PacketSender.cs:122-124 · BulkSenderPacket.cs:24

DispatchPendingBulkPacketOfType übergibt die lebende Liste an den BulkSenderPacket und leert sie direkt danach. Ist Configuration.EnablePacketQueue aktiv, serialisiert der Transport aber nicht inline — er reiht das Paket-Objekt ein und serialisiert später in Flush(). BulkSenderPacket ist nicht ILatencySensitivePacket, also wird es gequeued.

Fehlerhafter Ablauf
SendToConnection(conn, new BulkSenderPacket(packetId, pendingPackets), ReliableImmediate);
pendingPackets.Clear();   // BulkSenderPacket.SerializedInnerPackets zeigt auf DIESE Liste

// TransportPacketSender.SendToConnection

    || packet is ILatencySensitivePacket)
    return SendPacket(...);        // verlassen
queue.Enqueue((packet, sendType));  // BulkSenderPacket landet hier -> Flush() serialisiert leer
Fix

Snapshot vor dem Senden: var snapshot = new List<byte[]>(pendingPackets); und new BulkSenderPacket(packetId, snapshot) — oder BulkSenderPacket als ILatencySensitivePacket markieren. Betrifft alle batchbaren Typen (DragToolPacket, StorageItemPacket, PickupItemPacket, …). Default der Option ist false, aber sie ist persistiert und im Config sichtbar.

Packets/Core/ChunkedPacket.cs:14, 39-45, 74

Zusätzlich fehlt die Bounds-Prüfung chunks[ChunkIndex] gegen TotalChunks, und unvollständige Einträge werden nie entfernt.

public void OnDispatched()

Key auf (SenderConnectionId, SequenceId) umstellen — der Transport kennt den Sender in OnNetworkReceive bereits. Zusätzlich ChunkIndex/TotalChunks validieren und verwaiste Einträge nach Timeout aufräumen.

M6SaveChunkAssembler rät die Chunkgröße und kopiert unbegrenzt
Misc/World/SaveChunkAssembler.cs:97, 115-124

ChunkSize wird aus der Länge des ersten empfangenen Chunks geraten. Kommt zuletzt der kurze Abschluss-Chunk zuerst (Math.Min(chunkSize, totalSize - offset)), ist die Chunkgröße zu klein, TotalChunks wird zu groß, und chunkIndex = chunk.Offset / save.ChunkSize landet in falschen Slots. Buffer.BlockCopy prüft Offset + Length <= Data.Length nicht. Dazu greift der Retransmit nur, wenn mehr als die Hälfte der Chunks fehlt — ein zu 51 % fertiger Save hängt für immer auf dem Overlay.

Fix

Chunkgröße explizit im SaveFileChunkPacket mitschicken, Offset/Length validieren, die >50 %-Schwelle streichen und einen absoluten Abbruchpfad (z. B. 120 s) einbauen.
